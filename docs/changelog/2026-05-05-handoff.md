## 重要な知見

### OTel / CloudWatch Logs

| 設定 | 結果 |
|---|---|
| `DISABLE_ADOT_OBSERVABILITY=true` | Agent のアプリケーションログ（`sdpm.agent`）が CloudWatch に出なくなる ❌ |
| `OTEL_TRACES_EXPORTER=none` | トレースの 400 エラーが消え、アプリケーションログは維持される ✅ |
| デフォルト（何も設定しない） | トレースバッチが 1MB 超えで 400 エラー、5秒ごとにノイズ |

**現在の設定**: Agent / MCP Server 両方に `OTEL_TRACES_EXPORTER=none`

### Composer 接続切断の根本原因調査

#### 確認した事実

1. MCP Server の `run_python` は**同期関数**（`def run_python`）で、FastMCP は `asyncio.to_thread` を使わずに直接呼ぶ → **イベントループをブロックする**
2. ブロック中、MCP Server は他のリクエストを処理できない → ツール呼び出しが**完全に直列**で処理される
3. Composer は最大 10 グループを並行実行するが、MCP Server 側では 1 つずつしか処理されない
4. `run_python` の実行時間が 30〜47 秒に達する（Code Interpreter API 呼び出し）
5. 接続切断時、**MCP Server 自体は生きていた**（Ping に応答し続けていた）
6. 切断されたのは **Composer の MCPClient** のみ（メインの MCPClient は正常）

#### Strands SDK の `Connection to the MCP server was closed` 発生メカニズム

`MCPClient._invoke_on_background_thread` 内で:
```python
done, pending = await asyncio.wait([invoke_event, close_future], return_when=FIRST_COMPLETED)
if done.pop() == close_future:
    raise RuntimeError("Connection to the MCP server was closed")
```

`close_future` が完了する条件: `_async_background_thread` の `async with self._transport_callable()` が例外で抜けた時（= Streamable HTTP トランスポートが切断された時）

#### 未確定の部分

- Composer の MCPClient がリクエストを送信してから切断されるまでの正確な時間（`composer_tool_send` ログが旧コンテナのため未取得）
- トランスポートが切断された具体的な理由（httpx タイムアウト？サーバー側の切断？）
- AgentCore Runtime の Agent → MCP Server 間の通信経路の詳細

#### 次回再現時に確認すべきこと

新コンテナが動いていれば以下のログが出る:
- Agent: `composer_tool_send: group=N, tool=run_python, slugs=...`（送信時刻）
- MCP Server: `tool_start: tool=run_python`（処理開始時刻）
- MCP Server: `tool_ok: tool=run_python, duration=Ns`（完了時刻）
- Agent: `Tool error: tool=run_python, exception_type=..., error=...`（エラー時刻）

`composer_tool_send` と `tool_start` の差分 = キュー待ち時間。`composer_tool_send` が出ているのに `tool_start` が出ていなければ、リクエストが MCP Server に到達していない。

### 対策の方向性（未実装）

| 対策 | 効果 | 実装難易度 |
|---|---|---|
| `run_python` を `async def` + `asyncio.to_thread` に変更 | イベントループのブロック解消、並行処理可能に | 中（Code Interpreter API が同期なので to_thread でラップ） |
| `COMPOSER_MAX_CONCURRENCY` を下げる（10→3） | キュー深さ削減、待ち時間短縮 | 低（環境変数変更のみ） |
| MCPClient の timeout を延長（120→600） | 待ち時間が長くても切断されにくくなる | 低（mcp_clients.py 変更） |

### Cognito パスワード問題

CloudFormation が `UpdateUserPoolClient` を呼ぶ際に `ExplicitAuthFlows` を送信しないと、Cognito がデフォルト値にリセットし `ALLOW_USER_PASSWORD_AUTH` が消える。PR #112 のカスタムリソースが正しく `ExplicitAuthFlows` を含めて再設定するため、デプロイ後に自動復旧する。
