## オーケストレーション運用ルール

### レビュアーの活用（重要）
テスト結果が出たら、結論を出す前に必ずレビュアー（workspace:14）に以下を問う:
- 「このテスト結果から何が証明されたか？何が証明されていないか？」
- 「対策が有効と言い切れるか？言い切れない場合、何が足りないか？」
- 「結論に論理の飛躍がないか？」

オーケストレーターは実行に集中すると楽観バイアスがかかる。レビュアーは客観的なゲート役。
reviewer にはテスト結果ファイルのパスのみ送る。自分の結論を含めない。

### 共有コンテキスト方式
- `.orchestration/shared-context.md` に背景・環境・タスク・完了条件を集約（version管理）
- ワーカーへの指示は `.orchestration/task-*.md` に書いてパスを送る（cmux send の改行分割回避）
- 長時間タスクでは `.orchestration/` ディレクトリ（gitignore済み）も活用可

### steering 違反の観察
次回実行時に各ロールの行動を観察し、以下を確認:
- dev が3回で修正ループを止めるか
- reviewer がオーケストレーターの結論を無視して独立判断するか
- debugger がコードを変更しないか
違反があれば steering の表現を強化する。
